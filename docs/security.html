Security / Practical guide

Give a tool only the access it needs.

Start with one readable file. Check an attempted access outside that grant. Then apply the same boundary to an agent’s tool and inspect its approval requirement.

You need an installed Nexo CLI and a repository checkout. All commands below run from docs/security. The examples use local files only: no API key, model request, database or container is needed. Open the example files. For the architecture, see Nexo Shield.

1. Limit file access

The example folder contains public/report.txt with the text Orders ready: 2. The program grants access to that exact file and denies shell commands. Permission targets are resolved from the working directory, so enter the example folder first.

read.nexo
policy:
    allow read "public/report.txt"
    deny shell

read("public/report.txt")
print("Read permitted.")
From the repository root
cd docs/security
nexo check --effects --require-complete read.nexo
nexo security run read.nexo

The static check exits 0. The strict runtime command reads the file and prints Read permitted.. Static analysis inspects known requirements; security run enforces checked API access during execution. Neither command requests OS isolation.

2. Check an attempted access outside the grant

The next program retains the same policy but requests private.txt. That file does not need to exist: permission is refused before its contents can be read.

denied.nexo
policy:
    allow read "public/report.txt"
    deny shell

print(read("private.txt"))
Run each command separately; both are expected to fail
nexo check --effects denied.nexo
nexo security run denied.nexo

Both commands return exit code 1 and report the missing read grant. This is an expected denial. Under Shield, undeclared checked access is fatal and try cannot recover from a security violation. If an allow and a deny both match, the deny wins. Keep this example denied rather than broadening its policy.

3. Constrain an agent’s tool

The tool reads the same fixed file; the agent lists that tool and asks for confirmation. The example deliberately never calls support.handle, so checking it cannot invoke a provider.

agent.nexo
policy:
    allow read "public/report.txt"
    deny shell

@tool "Read the public order summary"
fn report() -> str!:
    return read("public/report.txt")?

agent support:
    tools = [report]
    goal = "Answer using the public order summary"
    max_steps = 3
    confirm = [report]

Source declarations describe the application. A separate, trusted operator manifest constrains model dispatch. It names the allowed agent and tool by file::symbol; identity paths are relative to the manifest directory. The agent and tool each receive only the read grant. The tool also requires human approval.

authorization.json
{
  "version": 1,
  "agents": {
    "agent.nexo::support": {
      "permissions": [
        [
          "allow",
          "read",
          "public/report.txt"
        ]
      ],
      "tools": [
        "agent.nexo::report"
      ]
    }
  },
  "tools": {
    "agent.nexo::report": {
      "permissions": [
        [
          "allow",
          "read",
          "public/report.txt"
        ]
      ],
      "confirm": true
    }
  }
}
Inspect configured permissions without running the agent
nexo check --effects --json --authorization authorization.json agent.nexo

In the summary whose function is report, the read effect has allowed comparisons for the root, agent and tool scopes, and approval_required is true. Each applicable scope must permit access; an agent grant cannot widen the program policy. The tool grant governs model dispatch, while a direct trusted call to the function remains an ordinary function call.

To try a denied configuration, copy authorization.json to no-tools.json and set the agent’s tools array to []. Check again with --authorization no-tools.json: it returns exit code 1 with a denied dispatch comparison. The model cannot add a grant to fix this.

4. Review unknowns and approval separately

The preceding check exits 0 in advisory mode, but its module summary still contains unknown registration effects. The complete report function summary does not make the entire module complete. You can make that distinction a failing check:

Expected exit code 1: the module summary is incomplete
nexo check --effects --json --require-complete \
  --authorization authorization.json agent.nexo

An unknown means the analyzer cannot establish the effect for that construct. It must not be interpreted as pure or permitted. --require-complete fails on unknowns without changing their warning severity. Read the full command and exit semantics.

The analysis never supplies approval. When you later connect a real provider, configure its destination and credential permissions too, then launch with nexo security run --authorization authorization.json agent.nexo. As supplied, this file only registers the tool and agent; it does not dispatch them. An actual support.handle(...) call needs provider setup and a human-input execution mode for confirmation. Keep the operator manifest and its parent directories outside the application’s writable grants. Read the dispatch and approval contract.

5. Choose the boundary your application needs

Permissions, credentials, API authentication and process isolation address different parts of an application. Continue with the guide that matches what you are building.

Your next taskContinue here
Use a real modelProvider setup and agents and tools. A fake answer helps test application logic; it does not prove the real dispatch boundary.
Keep credentials out of sourceSecrets, passwords and cryptography: pass secret values to supported consumers, use password.hash/password.check for passwords, and review key handling separately from file permissions.
Protect an HTTP APIJWT authentication and role tests, with the complete Web and HTTP guide and server reference. Authentication does not grant the server process additional Shield permissions.
Limit imported codeDependency and caller ceilings: use the same dependency manifest for static inspection and runtime enforcement.
Contain native executionHardened Docker and Linux worker requirements. Probe the deployment host; unsupported requested isolation must stop execution.

A static match is a snapshot of source, configuration and filesystem metadata. It cannot authorize changed artifacts or replace runtime checks, human approval or the chosen isolation boundary.
