Libraries

Libraries, step by step

Build services, coordinate work and manage application data. Follow practical guides for web APIs, AI, databases and streams, then add feature flags, privacy controls, deployment and recovery.

Example files live in docs/libraries in the repository checkout. Unless a command says otherwise, run it from its example’s folder. Displayed results come from executable examples; validation uses isolated copies so databases, exports and local state stay separate. No external provider is called by the executed examples. C/Python examples require their host integration tooling.

Adding credentials or model tools? Follow the security guide to check permissions, verify a denial and constrain an agent’s tools before connecting external services. The reference lists module options and language constructs.

nexo.web and HTTP: build and test an API

A server block defines routes; http calls them as a client. Start with a small registration endpoint, verify its inputs and responses, then add authentication. These examples return the submitted record; they do not create an account, persist data or send an email.

Run locally, test on a free port

No use or external service is needed for these APIs. From the repository checkout, run the first example’s tests:

From the repository root
nexo test docs/libraries/web/routes.nexo

In a test, Nexo starts the server on a free local port; signup.url contains its address. Use that URL rather than assuming port 8080. To try the example outside tests, run nexo docs/libraries/web/routes.nexo, visit http://localhost:8080/health, then stop it with Ctrl-C. The routes in this first example have no authentication; use them for the local exercise.

Typed routes and request bodies

get "/greet/{id}"(id: int, name: str = "visitor") takes id from the path and name from the query string. A post route with a record parameter validates the JSON body against that record before entering the handler. A missing required field or invalid typed path returns 400. A str field checks its type; it does not establish that an email address exists or belongs to the caller.

A text result becomes a text response. A record becomes JSON, with status 201 for a successful POST. The client’s .status, .text and .json() let tests inspect the response. These tests make real loopback requests, including invalid ones:

routes.nexo
type Registration:
    name: str
    email: str

server signup:
    port = 8080

    get "/health"():
        return "ready"

    get "/greet/{id}"(id: int, name: str = "visitor"):
        return "hello {name}, number {id}"

    post "/registrations"(entry: Registration):
        return entry

test "routes return text and JSON":
    health = http.get("{signup.url}/health")
    assert health.status == 200
    print(health.text)
    reply = http.post("{signup.url}/registrations", {"name": "Ana", "email": "ana@example.com"})
    assert reply.status == 201
    print(reply.status, reply.json()["name"])

test "path and query parameters are typed":
    reply = http.get("{signup.url}/greet/7?name=Ana")
    print(reply.text)
    try:
        http.get("{signup.url}/greet/not-a-number", retries: 0)
        fail("expected an invalid path parameter")
    else e is HTTPError:
        assert e.message == "GET {signup.url}/greet/not-a-number answered 400 Bad Request"
        print(e.message.replace(signup.url, "URL"))

test "missing record fields fail validation":
    try:
        http.post("{signup.url}/registrations", {"name": "Ana"}, retries: 0)
        fail("expected a missing email field")
    else e is HTTPError:
        assert e.message == "POST {signup.url}/registrations answered 400 Bad Request"
        print(e.message.replace(signup.url, "URL"))

Authentication and roles

Set auth = tokens to require a JWT by default. Mark only intentionally open routes with @public; use @role("admin") when a valid token also needs an admin role. The tests below distinguish a missing token (401) from a valid token with the wrong role (403), then verify the allowed request.

The example creates a fresh signing key and signs tokens directly inside tests. It is not a login implementation. For deployment, use a managed, stable signing secret through jwt(key: secret("JWT_KEY")), and issue a role only after your application has authenticated the user and established that role. Do not accept a caller-supplied role as authority. Follow the secrets and security references before connecting real users.

auth.nexo
# A fresh key per run is for this isolated example, not a deployment setting.
tokens = jwt(key: password.generate(32))

type Registration:
    name: str
    email: str

server signup:
    port = 8080
    auth = tokens

    @public
    get "/health"():
        return "ready"

    @role("admin")
    post "/registrations"(entry: Registration):
        return entry

test "the health route is public":
    assert http.get("{signup.url}/health").text == "ready"

test "a private route rejects a missing token":
    try:
        http.post("{signup.url}/registrations", {"name": "Ana", "email": "ana@example.com"}, retries: 0)
        fail("expected authentication to be required")
    else e is HTTPError:
        assert e.message == "POST {signup.url}/registrations answered 401 Unauthorized"
        print(e.message.replace(signup.url, "URL"))

test "a valid token still needs the required role":
    token = tokens.sign({"sub": "ana", "role": "reader"}, expires: 1h)
    try:
        http.post("{signup.url}/registrations", {"name": "Ana", "email": "ana@example.com"},
                  headers: {"Authorization": "Bearer {token}"}, retries: 0)
        fail("expected the admin role to be required")
    else e is HTTPError:
        assert e.message == "POST {signup.url}/registrations answered 403 Forbidden"
        print(e.message.replace(signup.url, "URL"))

test "an admin token opens the route":
    token = tokens.sign({"sub": "ana", "role": "admin"}, expires: 1h)
    reply = http.post("{signup.url}/registrations", {"name": "Ana", "email": "ana@example.com"},
                      headers: {"Authorization": "Bearer {token}"})
    assert reply.status == 201
    print(reply.status, reply.json()["name"])

HTTP failures, timeouts and retries

An HTTP response with status 400 or higher raises HTTPError; connection failures raise NetworkError. Use try/else when you expect an error response. In the examples, fail after each request ensures that a missing rejection fails the test instead of silently passing.

Requests accept headers:, timeout: and retries:. The default timeout is 30 seconds. GET, PUT and DELETE retry twice after a network error or a 502, 503 or 504. POST and PATCH do not retry by default because repeating them may repeat an effect. Set an appropriate timeout for the dependency you are calling; decide how duplicate writes will be handled before adding retries.

fake can replace a dependency in a test without contacting its service. Keep real HTTP tests for route validation and authentication, and use fakes when testing application logic around an unrelated external dependency. See the HTTP client and fake example for the call syntax.

Add persistence and execution boundaries

Continue with a web API backed by a database table when registrations must survive a restart. For all route options and error mappings, see the server reference.

JWT authentication controls who can call a route. Shield controls the protected operations the program can perform. Follow the security guide for grants, known effects and denials. The ordinary HTTP examples here are not Shield deployment profiles: dependency/authorization configurations reject external listeners; supported in-memory and loopback ingress profiles require explicit configuration. The offline Linux worker denies sockets.

nexo.ai: language models

ask is a function: it sends an instruction and an input to a model and returns its answer. Assigned to a typed variable, the answer is that type, checked field by field. It needs no use.

Set up a model

nexo ai setup asks for a provider, a model and the name of the environment variable that holds the key, and saves them for every program of your user. The key itself is never written in a file.

terminal
$ nexo ai setup
Provider (anthropic, openai, ollama, mistral, gemini, azure or bedrock): anthropic
Model (for example claude-opus): claude-opus
Environment variable that holds the key (for example ANTHROPIC_KEY): ANTHROPIC_KEY
Address (Enter for the usual one):
Configuration saved in ~/.config/nexo/ai.toml
$ export ANTHROPIC_KEY=...

To run models on your own machine, without a key or an account, install Ollama, run ollama pull llama3.2 and answer ollama and llama3.2. Any server that speaks OpenAI's API (Groq, OpenRouter, vLLM, LM Studio) is openai with its address.

A project can have its own settings in a nexo.toml, which applies to every program in its folder and below. [ai.prices] gives the price of each model, so that budget can count the spend; copy them from your provider's price list. [mcp.NAME] declares an MCP server whose tools an agent can use.

nexo.toml
# The project's settings, for every program in this folder and below.
[ai]
provider = "anthropic"
model = "claude-opus"
key = "ANTHROPIC_KEY"   # the name of the variable, never the key itself
budget = "5 EUR per day"

[ai.models]
fast = "anthropic:claude-haiku"
local = "ollama:llama3.2"

[ai.prices]   # EUR per million input and output tokens, from your provider's page
"anthropic:claude-opus" = ["14.00 EUR", "70.00 EUR"]
"anthropic:claude-haiku" = ["0.90 EUR", "4.50 EUR"]

[mcp.files]   # an MCP server an agent can use with tools = [mcp("files")]
command = ["npx", "-y", "@modelcontextprotocol/server-filesystem", "."]

A program can set the model itself with an ai: block. The settings come from the first place that has them: the call, its profile:, the program's ai block, nexo.toml, then the user's configuration. A policy: block says which hosts and variables the program may use; a release build needs one.

assistant.nexo
## The settings of nexo.ai inside a program: they win over nexo.toml.
policy:
    allow net "api.anthropic.com"
    allow net "localhost"
    allow env "ANTHROPIC_KEY"

ai:
    provider = "anthropic"
    model = "claude-opus"
    key = secret("ANTHROPIC_KEY")
    fallback = ["ollama:llama3.2"]
    budget = 5 EUR per day
    when_over_budget = "ollama:llama3.2"

ai models:
    fast = "anthropic:claude-haiku"
    local = "ollama:llama3.2"

ai profile "drafts":
    model = "fast"

fn title(text: str) -> str!:
    return ask("Write a title of at most six words", text, profile: "drafts")?

test "the title":
    fake ask returns "Nexo on the web"
    print(title("A long article about WebAssembly"))

Typed answers

The type of the variable tells the model what to answer, and the answer is checked against it: team is one of three words and urgency a number from 1 to 5. An answer that does not fit is sent back to the model with the reason, up to 3 times, and then the call fails with InvalidData. The rest of the program works with an ordinary record.

triage.nexo
## Sort support tickets with a typed answer from the model.
type Triage:
    team: "billing" | "shipping" | "tech"
    urgency: 1..5
    summary: str

type Ticket:
    id: int
    text: str

fn triage(t: Ticket) -> Triage!:
    answer: Triage = ask("Route this support ticket to a team", t.text, creativity: low)?
    return answer

fn route(t: Ticket) -> str!:
    r = triage(t)?
    var queue = r.team
    if r.urgency >= 4:
        queue = "{r.team}-now"
    return "#{t.id} -> {queue}: {r.summary}"

test "an urgent billing ticket goes to the front":
    fake ask returns Triage(team: "billing", urgency: 5, summary: "charged twice")
    print(route(Ticket(id: 7, text: "You charged my card twice!")))

test "a question waits in its queue":
    fake ask returns Triage(team: "tech", urgency: 2, summary: "how to export")
    print(route(Ticket(id: 8, text: "How do I export my data?")))
$ nexo test triage.nexo
#7 -> billing-now: charged twice
✓ an urgent billing ticket goes to the front
#8 -> tech: how to export
✓ a question waits in its queue
2 tests: 2 passed, 0 failed

Extract data from text

A typed answer can hold dates, money and lists of records, so text that people write becomes data a program can add up. The input goes to the model marked as data, never as instructions, which is the default guard against prompt injection, and @private fields are hidden from it.

extract.nexo
## Read the fields of an invoice out of an email.
type Line:
    item: str
    quantity: int
    price: money

type Invoice:
    number: str
    due: date
    lines: list[Line]

fn read_invoice(mail: str) -> Invoice!:
    invoice: Invoice = ask("Extract the invoice in this email", mail)?
    return invoice

fn total(i: Invoice) -> money:
    return i.lines |> map it.price * it.quantity |> sum

mail = """
Hi, attached is invoice F-2041, due on 15 November.
2 keyboards at 49.90 EUR and 1 monitor at 189.00 EUR.
"""

test "the fields come back typed":
    fake ask returns Invoice(number: "F-2041", due: date(2026, 11, 15), lines: [
        Line(item: "keyboard", quantity: 2, price: 49.90 EUR),
        Line(item: "monitor", quantity: 1, price: 189.00 EUR)])
    i = read_invoice(mail)
    print(i.number, i.due, len(i.lines), "lines")
    print("total", total(i))
    print("to pay in", i.due - date(2026, 10, 28))
$ nexo test extract.nexo
F-2041 2026-11-15 2 lines
total 288.80 EUR
to pay in 18 days
✓ the fields come back typed
1 test: 1 passed, 0 failed

Answers as they arrive

With stream: true the answer comes in pieces, and a for loop runs for each one as it arrives, so a person can start reading at once. A fake answer that is a list of texts gives those pieces.

stream.nexo
## Show an answer as it arrives, piece by piece.
fn explain(topic: str) -> str!:
    var text = ""
    for piece in ask("Explain in two sentences", topic, stream: true)?:
        print(piece, end: "")
        text += piece
    print()
    return text

test "the pieces arrive in order":
    fake ask returns ["Copy-on-write ", "shares a list ", "until one side changes it."]
    text = explain("copy-on-write")
    print(len(text), "characters")
$ nexo test stream.nexo
Copy-on-write shares a list until one side changes it.
54 characters
✓ the pieces arrive in order
1 test: 1 passed, 0 failed

Agents and tools

After learning the tool syntax below, use the operator-controlled tool example to add narrow grants and human approval. Faking an answer tests application logic; real dispatch permissions must be checked separately.

A function marked @tool "what it does" can be called by the model, with arguments checked against its parameter types. An agent block gives a model a goal, its tools and a limit of steps; a tool in confirm runs only after a person answers yes on the terminal. The tools are ordinary functions that you test directly, and fake support.handle replaces the agent's answer.

agent.nexo
## An agent that answers order questions with the program's own functions.
type Order:
    id: int
    status: "paid" | "shipped" | "delivered"
    email: str

orders = [
    Order(id: 7, status: "shipped", email: "ana@mail.com"),
    Order(id: 8, status: "paid", email: "luis@mail.com")]

@tool "Looks up an order by its number"
fn find_order(id: int) -> Order!:
    for o in orders:
        if o.id == id:
            return o
    fail("there is no order {id}")

@tool "Sends a short email to the customer of an order"
fn email_customer(id: int, text: str) -> str!:
    o = find_order(id)?
    return "sent to {o.email}"

agent support:
    model = "anthropic:claude-opus"
    tools = [find_order, email_customer]
    goal = "Answer questions about orders, politely and briefly"
    max_steps = 5
    confirm = [email_customer]

test "the tools are ordinary functions":
    print(find_order(7).status)
    try:
        find_order(99)
    else e:
        print(e.message)

test "the agent's answer can be faked":
    fake support.handle returns "Order 7 has shipped."
    print(support.handle("Where is my order 7?"))
$ nexo test agent.nexo
shipped
there is no order 99
✓ the tools are ordinary functions
Order 7 has shipped.
✓ the agent's answer can be faked
2 tests: 2 passed, 0 failed

nexo.db: databases

@table types are the schema, and a pipeline on a table becomes one parameterised SQL query. The same program runs on SQLite, PostgreSQL, MySQL, MongoDB and Elasticsearch: only the address changes.

Connect a database

SQLite is built in: connect("shop.db") opens the file, or creates it, and connect(":memory:") keeps the database in memory. For a server, the address names the user, host and database, and the password goes in key:, from an environment variable. A password written in the address is an error.

the address of each database
use nexo.db

db = connect("shop.db")                                                         # SQLite
db = connect("postgres://shop@db.example.com/shop", key: secret("DB_PASS"))      # PostgreSQL 14+
db = connect("mysql://shop@db.example.com/shop", key: secret("DB_PASS"))         # MySQL 8+
db = connect("mongodb://shop@db1.example.com,db2.example.com/shop", key: secret("DB_PASS"))
db = connect("elasticsearch://elastic@search.example.com:9200/shop", key: secret("ES_PASS"))

Nexo speaks each database's own protocol, so there is no driver to install. A server on another machine is reached over TLS, with its certificate checked against the system's authorities; SSL_CERT_FILE adds a certificate of your own. On your own machine, a server without TLS works too:

terminal
$ docker run -d -p 5432:5432 -e POSTGRES_USER=shop -e POSTGRES_PASSWORD=dev postgres:16
$ DB_PASS=dev nexo app.nexo     # with connect("postgres://shop@localhost/shop", key: secret("DB_PASS"))

The policy of a program that uses a server names its host and the variable of the password: allow net "db.example.com" and allow env "DB_PASS". On MongoDB and Elasticsearch, db.sql is an error, there is no schema to migrate, and a transaction undoes its writes when it fails but does not hide them from other programs before it ends.

Tables and queries

ref is a link to a row of another table and many the rows that link back. where, sort by, take, count, pick and group by run in the database, also through a ref (where member.city == "Rome"); a step that cannot be translated runs in memory, with the same result.

library.nexo
## A lending library: books, members and loans in SQLite.
use nexo.db

db = connect("library.db")

type Genre:
    Novel
    Science
    History

@table
type Book:
    id: id
    title: str @unique
    genre: Genre
    year: int
    loans: many Loan

@table
type Member:
    id: id
    name: str
    city: str
    loans: many Loan

@table
type Loan:
    id: id
    book: ref Book
    member: ref Member
    out: date
    back: date?

dune = db.Book.add(title: "Dune", genre: Novel, year: 1965)
cosmos = db.Book.add(title: "Cosmos", genre: Science, year: 1980)
spqr = db.Book.add(title: "SPQR", genre: History, year: 2015)
db.Book.add(title: "Solaris", genre: Novel, year: 1961)

ana = db.Member.add(name: "Ana", city: "Rome")
luis = db.Member.add(name: "Luis", city: "Lyon")

db.Loan.add(book: dune, member: ana, out: date(2026, 9, 2), back: date(2026, 9, 20))
db.Loan.add(book: cosmos, member: ana, out: date(2026, 10, 1))
db.Loan.add(book: spqr, member: luis, out: date(2026, 10, 12))
db.Loan.add(book: dune, member: luis, out: date(2026, 10, 15))

# each pipeline is one SQL query
print("novels:", db.Book |> where genre == Novel |> sort by year |> map it.title)
print("after 1970:", db.Book |> where year > 1970 |> count)
print("by genre:", db.Book |> group by genre |> count)

# a condition through a ref: the loans of members in Rome
print("from Rome:", db.Loan |> where member.city == "Rome" |> map it.book.title)

# books that are out: loans without a return date
for l in db.Loan |> where back == none |> sort by out:
    print("out:", l.book.title, "since", l.out, "with", l.member.name)

print("Dune has been lent", dune.loans.count(), "times")
print("Ana has", ana.loans |> where back == none |> count, "book at home")

Transactions

Everything inside db.transaction: is kept or undone together. The third transfer has already taken the money from Ana when it finds that Eva has no account, and the failure undoes that too. expect checks the amount before anything starts.

bank.nexo
## Transfers that either happen whole or not at all.
use nexo.db

db = connect(":memory:")

@table
type Account:
    id: id
    owner: str @unique
    balance: decimal

@table
type Movement:
    id: id
    account: ref Account
    amount: decimal
    note: str

fn transfer(from_owner: str, to_owner: str, amount: decimal) -> bool!:
    expect amount > 0
    db.transaction:
        a = db.Account.find(owner: from_owner)?
        if a.balance < amount:
            fail("{from_owner} has {a.balance}, not {amount}")
        db.Account.update(a, balance: a.balance - amount)
        db.Movement.add(account: a, amount: -amount, note: "to {to_owner}")
        # a failure from here on undoes the lines above too
        b = db.Account.find(owner: to_owner)?
        db.Account.update(b, balance: b.balance + amount)
        db.Movement.add(account: b, amount: amount, note: "from {from_owner}")
    return true

fn balances():
    for a in db.Account.all():
        print("  {a.owner}: {a.balance}")

db.Account.add(owner: "Ana", balance: 100.00)
db.Account.add(owner: "Luis", balance: 20.00)

fn attempt(from_owner: str, to_owner: str, amount: decimal):
    try:
        transfer(from_owner, to_owner, amount)
        print("sent {amount} from {from_owner} to {to_owner}")
    else e:
        print("refused ({e.kind}): {e.message}")

attempt("Ana", "Luis", 30.00)
attempt("Luis", "Ana", 80.00)
attempt("Ana", "Eva", 10.00)

print("only the first one happened:")
balances()
print(db.Movement.count(), "movements")
$ nexo bank.nexo
sent 30.00 from Ana to Luis
refused (Error): Luis has 50.00, not 80.00
refused (NotFound): There is no Account with owner = "Eva"
only the first one happened:
  Ana: 70.00
  Luis: 50.00
2 movements

The SQL it sends

Totals and groups are computed by the database, not by reading every row. NEXO_SQL_LOG=1 writes each statement to the error output, with its parameters: values never become part of the SQL text.

report.nexo
## A sales report computed by the database itself.
use nexo.db

db = connect(":memory:")

@table
type Sale:
    id: id
    region: str
    product: str
    units: int
    day: date

sales = [
    ["north", "pen", 30, 1],
    ["south", "pen", 12, 1],
    ["north", "ink", 5, 2],
    ["east", "pen", 8, 3],
    ["south", "ink", 20, 3],
    ["north", "pen", 14, 4],
]
for row in sales:
    db.Sale.add(region: row[0], product: row[1], units: row[2], day: date(2026, 10, row[3]))

print(db.Sale |> where product == "pen" |> group by region |> sum units)
print(db.Sale |> where day >= date(2026, 10, 3) |> pick region, units |> sort by units desc)
print(db.Sale |> group by product |> avg units)
print(db.Sale |> where units > 10 |> count)

nexo.stream: real-time data

A stream is one more source for when and |>. when handles each message; a pipeline groups them by time. A message whose block fails is tried 4 times and then goes to the dead letters, NAME.dead, so one bad message never stops the others.

Connect a broker

A source without a broker address is on the local broker, which needs no setup: files in .nexo/streams shared by the programs of your machine. That is enough to develop, and nexo test uses an in-memory broker that starts empty for each test. An option of a broker or a cloud puts the same source there, and nothing else in the program changes:

the sources of each broker
use nexo.stream

kafka("orders")                                              # the local broker
kafka("orders", partitions: 4)                               # local, 4 partitions
kafka("orders", servers: "shop@kafka1.example.com:9092,kafka2.example.com:9092", key: secret("KAFKA_PASS"))
rabbit("orders", url: "amqps://shop@mq.example.com/", key: secret("RABBIT_PASS"))
eventhub("clicks", namespace: "shop")                        # Azure Event Hubs
servicebus("orders", namespace: "shop")                      # Azure Service Bus
sqs("orders", region: "eu-west-1")                           # AWS SQS

websocket("wss://feed.example.com/prices")

key: is the broker's password, from an environment variable. A broker on another machine is reached over TLS only. The policy names the broker's host: allow net "kafka1.example.com".

Each message once

A broker delivers a message at least once, so after a failure it can arrive twice. With key:, a key already handled is acknowledged without running the block again. validate turns the JSON of a message into a record, and a message that does not fit goes to the dead letters with the reason.

payments.nexo
## Handle each payment once, even when the broker delivers it twice.
use nexo.stream

type Payment:
    id: str
    account: str
    cents: int

var balances: map[str, int] = {}

# key: a payment id already handled is acknowledged without running again
when kafka("payments") as msg, key: msg.json()["id"]:
    p: Payment = validate(msg.json(), as: Payment)?
    if p.cents <= 0:
        fail("payment {p.id} has {p.cents} cents")
    if not (p.account in balances):
        balances[p.account] = 0
    balances[p.account] += p.cents
    print("applied", p.id, "to", p.account)

test "a repeated payment is applied once":
    payments = kafka("payments")
    payments.send({"id": "p1", "account": "ana", "cents": 2000})
    payments.send({"id": "p2", "account": "ana", "cents": 550})
    payments.send({"id": "p1", "account": "ana", "cents": 2000})
    print(balances)

test "a bad message goes to the dead letters":
    kafka("payments").send({"id": "p3", "account": "luis", "cents": -100})
    kafka("payments").send({"id": "p4", "account": "luis"})

Windows of time

A pipeline on a stream groups its messages by the time they happened: window 1m by minute, sliding 5m over the last five minutes on every message, and session 30s until 30 seconds pass without a message. In a test, send(..., at: time) sets the time of each message.

windows.nexo
## Group the messages of a stream by time.
use nexo.stream

fn per_minute(row):
    print("minute     ", row)

fn last_five(total):
    print("last 5 min ", total)

fn visit(pages):
    print("visit       pages:", pages)

# tumbling: one result per minute and page
kafka("clicks")
  |> window 1m
  |> group by page
  |> count
  |> each per_minute

# sliding: on every message, over the messages of the last 5 minutes
kafka("sales")
  |> sliding 5m
  |> map amount
  |> sum
  |> each last_five

# session: the pages of a visit, which ends after 30 seconds without a click
kafka("visits")
  |> session 30s
  |> count
  |> each visit

Producer and consumer

A program with when handlers keeps reading until it is stopped. It saves the position it reached, so a second run reads only new messages. One program sends and another, in another terminal, reads:

for i in 1..3:
    orders.send({"id": i, "total": i * 25})
print("sent 3 orders")

## Read the orders, in another process, until it is stopped (Ctrl+C).
use nexo.stream

type Order:
    id: int
    total: int

    o: Order = validate(msg.json(), as: Order)?

nexo.sync: coordinate concurrent work

Use workers when independent tasks need to exchange results. Channels carry messages, select waits for a message or timeout, and shared marks state that tasks may change together. Start with a fixed number of workers and an explicit way to know when their work is complete.

A bounded worker queue

use nexo.sync enables these constructs. spawn f(args) launches a task and lets its caller continue. It does not return a join handle; the process waits for spawned tasks before normal shutdown. In this example, receiving one subtotal from each worker gives the main task an explicit completion point.

channel[int](size: 2) holds at most two queued integers. send waits when the queue is full, which prevents this producer from running arbitrarily far ahead. receive waits when the queue is empty. Two workers consume each job once between them; a channel is not a broadcast.

workers.nexo
use nexo.sync

fn produce(jobs: channel[int]):
    for n in 1..6:
        jobs.send(n)
    jobs.close()

fn worker(jobs: channel[int], results: channel[int]):
    var subtotal = 0
    for n in jobs:
        subtotal += n * 2
    results.send(subtotal)

jobs = channel[int](size: 2)
results = channel[int](size: 2)
spawn produce(jobs)
repeat 2:
    spawn worker(jobs, results)

var total = 0
repeat 2:
    total += results.receive()
assert total == 42
print("total:", total)
$ nexo workers.nexo
total: 42

The producer closes the jobs channel after its final send. Workers drain the remaining values and then leave their for loops. Each sends exactly one subtotal. The division of jobs between workers may vary, but the combined total is always 42. Only the main task prints, so scheduling does not change the displayed result.

Closure means “no more messages”; it does not discard queued values. Sending after closure is an error. Give one producer responsibility for closing the queue, or coordinate multiple producers before closing it. An empty queue with no future sender and no closure can leave a consumer waiting.

Wait for a message or a timeout

select can wait on several channel branches. A branch receives one available message. An after branch provides a timeout when no message arrives. Here the first selection consumes the queued alert; the second reaches its timeout because the queue is now empty.

select.nexo
use nexo.sync

alerts = channel[str](size: 1)
alerts.send("disk full")

select:
    message from alerts:
        print("alert:", message)
    after 1s:
        fail("the queued alert should be ready")

select:
    message from alerts:
        fail("the alert was already consumed")
    after 1ms:
        print("no more alerts")
$ nexo select.nexo
alert: disk full
no more alerts

A timeout ends this wait; it does not cancel a worker or close its channel. Arrange shutdown separately. Do not depend on a particular task scheduling order when several sources can produce messages.

Share state deliberately

Ordinary task-owned values are not a place for workers to accumulate shared mutations. Prefer channels for passing results. When tasks need a common map, declare it with shared. Statements that use shared state run under the shared lock; that does not turn several separate statements into a transaction.

shared.nexo
use nexo.sync

shared seen = {}

fn remember(n: int):
    seen[n] = n * 2

parallel for n in 1..6:
    remember(n)

assert len(seen) == 6
assert seen[4] == 8
print("entries:", len(seen))
print("entry 4:", seen[4])
$ nexo shared.nexo
entries: 6
entry 4: 8

The parallel for finishes before the assertions run. Each iteration writes a distinct key, so the final map has six entries regardless of scheduling. Keep shared operations short and avoid relying on map iteration order. See the concurrency reference for the surrounding language constructs.

Recognize a queue deadlock

A bounded queue needs a receiver that can make progress. In this deliberately failing example, the first send fills the only slot. The second send waits for room, but there is no other task to receive anything.

deadlock.nexo
use nexo.sync

jobs = channel[int](size: 1)
jobs.send(1)
# The only task waits for room, but no receiver can free a slot.
jobs.send(2)
$ nexo deadlock.nexo
Error in deadlock.nexo, line 6:
  jobs.send(2)
  ^^^^^^^^^^^^
Every task is waiting on a channel and none can go on. Close the channel with close() when there is nothing more to send, or send what another task waits for.

This command is expected to exit with code 1. Nexo reports that every task is waiting instead of hanging indefinitely on these channel waits. Start a receiver before filling the queue, or structure the producer/consumer lifecycle as in the worker example. Increasing the buffer only postpones this design error. Deadlock detection is not a general timeout for arbitrary blocking external operations.

Choose sync, streams or an execution boundary

Channels coordinate tasks inside one running process. They do not provide a durable broker, replay after a restart or cross-process delivery. Use streams and message brokers for those requirements. There is no task handle or per-task cancellation API in this interface.

Under Shield, spawned tasks retain the caller’s captured permission ceilings; launching a task cannot regain broader root permissions. Configured dependency/agent/tool boundaries restrict messages and shared values to supported plain data. The Linux worker profiles reject threads and sync imports. See the spawn security contract and security guide before choosing a deployment profile.

Feature flags: roll out a change deliberately

A flag changes which application path runs without changing its source. Flags are available implicitly: declare a flags: block, then call flag(name, user?). Use a flag for rollout decisions; keep authorization in your authentication and permission checks.

Switches, audiences and stable cohorts

on and off are global switches. users where evaluates a condition against the supplied user. A percentage chooses a stable cohort using the flag name and user identity, rather than making a fresh random decision for each request. Supply a stable user ID; 10% does not mean exactly one in every ten requests or exactly 10% of a small sample.

rollout.nexo
type User:
    id: int
    country: str

flags:
    checkout = off
    preview = 10%
    regional_help = users where country == "ES"
    old_design = on, expires: 2099-03-01

ana = User(id: 7, country: "ES")
luis = User(id: 8, country: "FR")
assert flag("preview", ana) == flag("preview", ana)
print("checkout:", flag("checkout"))
print("regional:", flag("regional_help", ana), flag("regional_help", luis))
print("stable cohort:", flag("preview", ana) == flag("preview", ana))
$ nexo rollout.nexo
checkout: false
regional: true false
stable cohort: true

Change the local override

Run these commands in the example folder. The first invocation uses the declared default. The setter writes an override to the local .nexo/flags.json store; the next invocation reads it. This example does not contact a hosted flag service.

$ nexo rollout.nexo
checkout: false
regional: true false
stable cohort: true
$ nexo flags set checkout on rollout.nexo
checkout = on (stage default)
$ nexo rollout.nexo
checkout: true
regional: true false
stable cohort: true

Use nexo flags set checkout off rollout.nexo to switch it back. Add --stage prod to set a production-stage override; the running application must select the matching stage, such as through NEXO_STAGE=prod. Keep stage and working-directory configuration consistent between the setter and application. Protect the override store from untrusted writes.

Retire flags after the rollout

expires: lets lint report a flag past its intended lifetime; it is not an automatic kill switch. Test both application paths, decide what happens when the feature is disabled, and remove the flag when its migration is complete. See the flag syntax reference.

Privacy: know where personal data goes

Mark data at its record definition, then follow it through storage, logs, export and deletion. These operations help implement application behavior; they do not establish a complete privacy policy or manage copies held by other systems.

Retention, export, erasure and restriction

@personal identifies personal fields. purpose records why a type is retained. keep = 2 years after last_seen makes old rows eligible for removal by the runtime’s retention sweep when the table is used, with subsequent sweeps at its configured interval. It is not a separate background deletion service.

The example uses future dates for its two fixtures so they remain outside the retention cutoff. It declares a retention rule but does not force a sweep or claim that an old row inserted after a sweep disappears immediately. It creates only a temporary local SQLite database when run by this documentation’s validation. Running the source yourself creates files in your working directory.

records.nexo
use nexo.db

db = connect("contacts.db")

@table
type Contact:
    id: id
    name: str @personal
    email: str @personal
    last_seen: date

    keep = 2 years after last_seen
    purpose = "answer support requests"

ana = db.Contact.add(name: "Ana", email: "ana@example.com", last_seen: date(2099, 1, 1))
luis = db.Contact.add(name: "Luis", email: "luis@example.com", last_seen: date(2099, 1, 1))
assert db.Contact.count() == 2
print("contacts before changes:", db.Contact.count())
path = privacy.export(ana)
assert len(read(path)) > 0
print("export:", path)
privacy.erase(ana)
privacy.restrict(luis)
assert db.Contact.count() == 0
print("visible contacts:", db.Contact.count())
print("physical rows:", len(db.sql("SELECT id FROM contact")))
$ nexo records.nexo
contacts before changes: 2
export: contact-1.json
visible contacts: 0
physical rows: 1

privacy.export writes a JSON export containing personal data: handle that file as sensitive. Erasure removes or anonymizes the record according to the supported storage semantics. Restriction hides the remaining record from ordinary queries, but does not physically delete it: the raw SQL count deliberately shows that one row remains. Direct SQL and external consumers need their own controls.

Private fields and logs

@private adds redaction when a record is passed to log. This example uses a dummy token:

logging.nexo
type Session:
    user: str
    token: str @private

log(Session(user: "ana", token: "example-token-not-a-real-credential"))
$ nexo logging.nexo

Redaction is not general information-flow tracking: do not extract a private field and print or concatenate it into a message. For database storage, @private columns require the connection’s encryption key, for example connect("contacts.db", key: secret("DB_KEY")). Keep that key outside source and manage its availability separately. The secret and cryptography APIs explain supported consumers.

C and Python: reuse an existing library

Use interoperability when an existing library supplies behavior your application needs. Both integrations need the relevant host runtime or toolchain; an import is executable integration, not a declaration that automatically contains third-party code.

Import a Python module

use python statistics as stats loads Python’s standard-library module under a local name. Numbers, text, lists and maps can cross the boundary. This example needs no third-party Python package:

python.nexo
use python statistics as stats

assert stats.mean([2, 4, 6]) == 4
print("mean:", stats.mean([2, 4, 6]))
print("median:", stats.median([9, 1, 5]))
$ nexo python.nexo
mean: 4
median: 5

For another module, install it in the Python environment used by the Nexo integration and test its availability on the deployment host. A dependency installed in an unrelated virtual environment may not be visible there. Conversion support does not imply that arbitrary Python objects behave like Nexo records or that Python calls are pure.

Check a C signature

use c "libm" uses the system math library. C integration requires the supported C header discovery/toolchain and the library on the host. Keep headers and the linked library consistent.

print("power:", libm.pow(2, 5))
$ nexo c.nexo

Resilience and workflows: make failure behavior explicit

These are language constructs and ordinary functions rather than extra modules to import. Decide whether an operation can safely be repeated, which failures are recoverable, and how completed side effects will be compensated.

Bound retries and provide an explicit fallback

This local simulation tries at most twice, then returns a cached value. It verifies both recovery on the second attempt and exhaustion. The simulated provider has no external side effects and no delay; this is not a general retry decorator.

retry.nexo
var attempts = 0
var unavailable = false

fn fetch() -> str!:
    attempts += 1
    if unavailable or attempts < 2:
        fail("temporary failure")
    return "fresh value"

fn fetch_with_fallback() -> str:
    repeat 2:
        try:
            return fetch()
        else e:
            print("attempt failed:", e.message)
    return "cached value"

assert fetch_with_fallback() == "fresh value"
assert attempts == 2
print("attempts:", attempts)

attempts = 0
unavailable = true
assert fetch_with_fallback() == "cached value"
print("fallback after", attempts, "attempts")
$ nexo retry.nexo
attempt failed: temporary failure
attempts: 2
attempt failed: temporary failure
attempt failed: temporary failure
fallback after 2 attempts

Real retry policy should select transient failures, bound elapsed time and account for repeated effects. A cached result has different freshness semantics from a successful live request: make that tradeoff explicit to callers. For built-in HTTP timeouts and method-specific retries, use the HTTP client guide. Do not stack retries without calculating the total attempt budget.

Stop calling a failing dependency

protect(provider, fails: 2, wait: 1m) opens a circuit after two consecutive failures. While open, it raises CircuitOpen without invoking the protected block. The example’s third request takes that path; the one-minute window does not make this program sleep for a minute.

circuit.nexo
fn provider(amount: int) -> int!:
    if amount < 0:
        fail("provider unavailable")
    return amount

fn guarded(amount: int) -> int!:
    var value = 0
    protect(provider, fails: 2, wait: 1m):
        value = provider(amount)?
    return value

for amount in [-1, -2, 5]:
    try:
        print(guarded(amount))
    else e is CircuitOpen:
        print("circuit open: use the local fallback")
    else e:
        print(e.message)
$ nexo circuit.nexo
provider unavailable
provider unavailable
circuit open: use the local fallback

The circuit’s local state is not a durable or distributed failure counter. Choose an appropriate fallback or propagate the failure. See the patterns reference for state machines and the surrounding constructs.

Undo an application action

An action declares its forward operation and an undo. Calls are remembered for reversal in the current action history. Here two list edits are undone in reverse order; this history is not the durable workflow store.

actions.nexo
var lines = ["first"]

action add(line: str):
    do: lines = lines + [line]
    undo: lines = [l for l in lines if l != line]

add("second")
add("third")
print(lines)
undo()
print(lines)
print(undo(), undo())
print(lines)

assert lines == ["first"]
$ nexo actions.nexo
["first", "second", "third"]
["first", "second"]
true false
["first"]

Compensate completed workflow steps

A workflow saves step progress in .nexo/workflows/. A failure runs the completed steps’ declared compensations in reverse order. The example creates an account, confirms it and sends a welcome message; the simulated failed delivery removes only that failed signup.

workflow.nexo
var accounts = []

fn create_account(email: str):
    accounts = accounts + [email]

fn delete_account(email: str):
    accounts = [a for a in accounts if a != email]

fn confirmed(email: str) -> bool:
    return email in accounts

fn send_welcome(email: str):
    if email.ends_with(".invalid"):
        fail("no mailbox for {email}")
    print("welcome,", email)

workflow customer_signup(email: str):
    step create_account(email)
        undo delete_account(email)
    step wait confirmed(email), max: 3 days
    step send_welcome(email)

customer_signup("ana@example.com")
try:
    customer_signup("bob@example.invalid")
else e:
    print(e.message)
print(accounts)

assert accounts == ["ana@example.com"]
$ nexo workflow.nexo
welcome, ana@example.com
no mailbox for bob@example.invalid
["ana@example.com"]

State is saved after completed steps; a process interrupted between an external effect and its progress save may repeat that effect on restart. Use idempotent operations or external deduplication where required. The local journal is not a transaction with a remote service, and compensation does not automatically reverse arbitrary effects. Successful runs remove their workflow journal; calling again with the same arguments starts a new run.

The sample tests compensation in one process, not a crash-recovery guarantee. A step wait condition, max: ... requires a deadline. Keep journal storage durable and protected when using restart recovery. Persistent workflows are rejected under Shield because their state confinement is not implemented. Continue with the workflow reference and execution boundaries.
