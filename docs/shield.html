Native code.
Clear boundaries.

Policy alone does not prevent DNS rebinding, mediate direct native syscalls or impose process resource limits. Explicit supported worker profiles provide separate kernel confinement and broker address pinning.

Choose which files your program can read and write. Shield checks those permissions when the program runs, and Docker adds a separate boundary around its execution.

Read a policy

Three rules. A clear boundary.

A policy: block declares the access your program is allowed to use. Read the example above as a short agreement between the program and the person running it.

Read

Open the input file

allow read "input.txt" permits reading that file. The call read("input.txt") uses this permission to load the text.

Write

Save the result

allow write "/out" permits writing inside the output directory. The call write("/out/result.txt", text) saves the text there.

Deny

Keep commands closed

deny shell forbids shell commands. A deny rule takes precedence over an allow rule, and undeclared checked access is rejected.

If this program tries to read private.txt, there is no permission for that file, so Shield stops execution. A permission failure cannot be handled with try. Keep grants narrow and add only the access the program needs.

Before execution

Inspect the access your code needs.

Static effect analysis follows supported calls and compares known permission requirements before you run the program. It is available in both the interpreter and compiler.

Check your source and existing Shield manifests
nexo check --effects app.nexo
nexo check --effects --json --require-complete \
  --dependencies permissions.json --authorization grants.json app.nexo

Permissions

Compare known requirements

Reports retain the source of each effect and compare it with the root policy, relevant dependency and caller ceilings, and configured tool and agent permissions. A denied possible call path is reported even if another path allows it.

Approval

Keep human decisions explicit

The report identifies operator-required approval, including for a pure configured tool. Reading a manifest and checking a program never grant that approval or dispatch a tool.

Completeness

Make unknowns visible

Dynamic targets, unresolved callbacks and opaque registration contexts remain unknown. They are advisory by default; --require-complete returns a failure for incomplete summaries. Analysis limits also produce explicit unknowns.

A static match describes the source, configuration and filesystem snapshot at analysis time. It is not an execution authorization or an isolation guarantee. Runtime permission checks, allowlists, approvals and the selected execution boundary still apply. Read the commands, options and exit codes.

01 / Architecture

Permission at every layer.

The person running the program supplies its trusted policy and configuration. Docker contains compilation and execution. The optional Linux worker adds filesystem and system-call restrictions around the compiled program.

02 / Capabilities

Small permissions.
Deliberate enforcement.

Shield builds on Nexo’s existing policy syntax, with strict decisions and additional boundaries selected by the operator.

01 / Authorization

Strict API decisions

A policy is required. Undeclared checked accesses stop execution, deny overrides allow, and policy violations cannot be caught with try.

02 / Dependencies

Dependency ceilings

--dependencies permissions.json intersects application, lexical module and active caller permissions. Permission snapshots cover joined tasks, tools, events and in-memory streams, with bounded plain-data transfers.

03 / Isolation

Offline kernel confinement

The Linux worker pins filesystem grants with openat2, enforces them with Landlock and installs a seccomp allowlist. It cannot create sockets, threads or child processes.

04 / Limits

Resource budgets

Docker bounds container memory, CPU and process count. The worker adds hard CPU, address-space, file-size and descriptor limits plus a supervised wall deadline.

05 / Visibility

Local decision traces

security trace emits JSON events on stderr with operation, decision and reason. Every target is redacted. Program output and ordinary diagnostics are not sanitized by this event format.

06 / Inspection

Inspect before running

security check validates code and displays policy without executing the program. security audit also shows the existing C inventory; it is not a vulnerability scanner.

03 / Deployment

From checkout to container.

Use Docker Engine on Linux x86_64 with cgroup v2. The image packages the compiler, static runtime and worker; production execution needs neither Python nor a Rust toolchain.

From the repository root, build the production image and run its demo. It reads /app/input.txt and writes /out/result.txt.

The demo prints Shield Docker: ok. Output is temporary unless an existing output directory is mounted.

Optional / Kernel isolation

Add Linux worker isolation

The default command already uses Docker and strict permission checks. To add the Linux worker, probe your deployment host, then run the same example with worker isolation. This requires Landlock ABI 3 or newer, seccomp, openat2, pidfds and a non-root identity.

Require the Linux offline worker
docker/shield/run.sh probe --require-linux
docker/shield/run.sh run-linux /app/main.nexo

Exit 0 means the strict probe passed. Exit 125 means setup or a requested guarantee is unavailable. Shield does not silently fall back.

Your project / Your output

Bring your own project

The project and output directories must already exist and be disjoint. The project is mounted read-only; only the output mount is writable. The helper maps the current non-root UID/GID, using 10001 when invoked as root.

Existing, separate project and output directories
docker/shield/run.sh --project ./project --output ./results \
    run-linux /app/main.nexo

Defaults: 512 MiB RAM, one CPU, 64 processes, no swap, a read-only root, no external network, and temporary storage for compilation and output. The entrypoint refuses execution when required effective guarantees are absent. Builds need network access; execution is offline.

04 / Boundaries

Clear about the limits, too.

The operator, policy, compiler and host configuration are trusted. Container isolation shares the host kernel. Each deployment host must pass its own strict probe.

Network

Offline by design

The Linux profile denies all sockets, including localhost and DNS. Network grants are rejected. Use this profile for work that does not require network access.

Native integrations

Integrations stay closed

In-process C, Python and shell integrations are rejected under Shield, even if allowed by policy. These integrations are outside the supported execution boundary.

Execution contexts

Conservative contexts

The socket-denying worker rejects threads; API profiles retain contexts across joined tasks and in-memory deferred work. Unsupported remote connectors and MCP fail closed. Persistent workflows are rejected before state loading or steps because their state operations bypass ordinary API policy.

API checks alone do not prevent filesystem races or DNS rebinding. Docker alone does not enforce per-policy filesystem grants. The Linux worker requires existing, disjoint positive filesystem grants and rejects deny exceptions it cannot represent faithfully. Operator manifests authorize named agents and tools. Full information-flow tracking and package-registry permissions remain unavailable. Policy alone does not mediate direct native syscalls or impose process resource limits.
