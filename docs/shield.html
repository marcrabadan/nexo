Nexo Shield

Native execution.
Explicit permissions.

Declare what your program may do. Shield enforces those permissions, narrows them across dependencies and can run compiled Nexo inside a hardened Docker container with an offline Linux worker.

Run with DockerExplore the architecture

Strict API checks in both implementations. A native Rust compiler/runtime and worker in the production image. Kernel isolation is requested explicitly.

docker/shield/example/main.nexo
policy:
    allow read "input.txt"
    allow write "/out"
    deny shell

text = read("input.txt")
write("/out/result.txt", text)
print("Shield Docker: {text}")

Architecture

From declared intent to kernel enforcement

The operator supplies trusted policy and configuration. Docker surrounds compilation and execution; requesting the Linux profile adds a dedicated worker boundary around the compiled program.

Features

Permissions that stay explicit

Shield builds on Nexo’s existing policy syntax, with strict decisions and additional boundaries selected by the operator.

Strict API decisions

A policy is required. Undeclared checked accesses stop execution, deny overrides allow, and policy violations cannot be caught with try.

Dependency ceilings

--dependencies permissions.json intersects application, lexical module and active caller permissions. The current profile supports synchronous code and bounded plain-data returns.

Offline kernel confinement

The Linux worker pins filesystem grants with openat2, enforces them with Landlock and installs a seccomp allowlist. It cannot create sockets, threads or child processes.

Resource budgets

Docker bounds container memory, CPU and process count. The worker adds hard CPU, address-space, file-size and descriptor limits plus a supervised wall deadline.

Local decision traces

security trace emits JSON events on stderr with operation, decision and reason. Every target is redacted. Program output and ordinary diagnostics are not sanitized by this event format.

Inspect before running

security check validates code and displays policy without executing the program. security audit also shows the existing C inventory; it is not a vulnerability scanner.

Docker deployment

Build the checkout. Run the native runtime.

Use Docker Engine on Linux x86_64 with cgroup v2. The image packages the compiler, static runtime and worker; production execution needs neither Python nor a Rust toolchain.

1. Try the packaged example

From a checkout containing Shield, build the production image and run its demo. It reads /app/input.txt and writes /out/result.txt.

From the repository root
docker/shield/build.sh runtime
docker/shield/run.sh

The demo prints Shield Docker: ok. Output is temporary unless an existing output directory is mounted.

2. Require the Linux profile

Probe the actual deployment host, then run the same example with worker isolation. This requires Landlock ABI 3 or newer, seccomp, openat2, pidfds and a non-root identity.

Require the Linux offline worker
docker/shield/run.sh probe --require-linux
docker/shield/run.sh run-linux /app/main.nexo

Exit 0 means the strict probe passed. Exit 125 means setup or a requested guarantee is unavailable. Shield does not silently fall back.

Bring your own project

The project and output directories must already exist and be disjoint. The project is mounted read-only; only the output mount is writable. The helper maps the current non-root UID/GID, using 10001 when invoked as root.

Existing, separate project and output directories
docker/shield/run.sh --project ./project --output ./results \
    run-linux /app/main.nexo

Defaults: 512 MiB RAM, one CPU, 64 processes, no swap, a read-only root, no external network, and temporary storage for compilation and output. The entrypoint refuses execution when required effective guarantees are absent. Builds need network access; execution is offline.

Security boundaries

Know exactly what you are enabling

The operator, policy, compiler and host configuration are trusted. Container isolation shares the host kernel. Each deployment host must pass its own strict probe.

Offline by design

The Linux profile denies all sockets, including localhost and DNS. Network grants are rejected. An online isolated profile with DNS/IP pinning and reviewed proxy handling is still future work.

Native integrations stay closed

In-process C, Python and shell integrations are rejected under Shield, even if allowed by policy. An independent native worker exists; a typed RPC bridge into Nexo is not implemented.

Conservative contexts

Async execution is rejected in the worker/dependency profiles until contexts can follow queued work. Persistent workflows are rejected before state loading or steps because their state operations bypass ordinary API policy.

API checks alone do not prevent filesystem races or DNS rebinding. Docker alone does not enforce per-policy filesystem grants. The Linux worker requires existing, disjoint positive filesystem grants and rejects deny exceptions it cannot represent faithfully. Full information-flow tracking, agent/tool authorization and package-registry permissions are not implemented.
