Application walkthrough

Build a support inbox

Connect a Nexo browser interface to an authenticated Nexo API, save requests in SQLite and generate a summary through a bounded agent.

This local application uses a fixed model stub, so no account, paid model call or cloud deployment is required. Its sample-request button works within the current browser input capabilities; it is not a free-text ticket editor.

How the pieces connect

  1. Nexo Web

    A typed read lists tickets. A mutation submits a sample request and reloads the list.

  2. Local gateway

    A Python helper serves assets, injects a CSRF token and translates the demo session to a signed backend token.

  3. Nexo Backend

    A role-protected route calls an agent, then stores the request and summary in SQLite.

The agent calls a fixed OpenAI-compatible fixture in the gateway. It returns a preset sentence and synthetic usage counts, not a generated answer or real billing data. The agent has no tools, one step and an 800-token invocation allowance.

There is one shared local demo identity. The helper creates it automatically; it demonstrates session transport and backend token validation, not a user login or multi-user account system.

1. Run the application

Start with the repository installation. From its root, activate the Python environment and run:

source .venv/bin/activate
python docs/walkthrough/support/run.py --state /tmp/nexo-support-demo

Open http://127.0.0.1:8765/ and click Add sample request. The list should show the original request and “A customer reports a duplicate order charge.” Refresh the page to read the saved row.

The helper builds the frontend, generates temporary server-side credentials and starts loopback listeners on ports 8765 and 8081. Keep both ports free. SQLite lives at /tmp/nexo-support-demo/support.db; assets live in that directory’s dist/. Ctrl+C stops both services. Reusing the directory preserves tickets; choose a new directory for a clean run.

2. Follow the source

Browser component
The load uses list[Ticket]; the mutation accepts a NewTicket and invalidates the list on success. Loading and errors are visible.
API, database and agent
JWT authentication and the support role protect both ticket routes. The route validates text length, requests a summary and stores the result.
Local session gateway and model stub
The Python helper binds loopback, checks Host, verifies Origin and CSRF for writes, and forwards only the fixed ticket endpoint. Browser code never receives the backend bearer token.
Project configuration
Required alongside the browser source when downloading the project.
Integration test
Checks session denial, CSRF denial, a real API write, the fixed model response and database-backed reads.

All files are in docs/walkthrough/support/. The helper serves only generated assets; it does not expose the database or source directory.

3. Verify security boundaries

python -m nexo security check docs/walkthrough/support/backend.nexo
python -m nexo security run docs/walkthrough/support/denied.nexo

The first command validates source and displays policy without executing it. The second is an intentional failure: the denial fixture attempts a read outside its grant. It should exit with a permission diagnostic.

The backend policy grants its database path, two secret environment variables and loopback network access. That hostname grant allows loopback generally; it is not a per-port allowlist. The application launched above uses ordinary development execution, not a Shield sandbox. The denial fixture proves only checked API enforcement.

The offline Linux worker denies sockets, so it cannot run this networked application unchanged. Shield’s bounded ingress has separate lifetime, connector and write restrictions; it is not production hosting for this inbox. Review Shield profiles before choosing containment. Docker and worker process limits are separate from agent token allowances.

4. Test and prepare delivery

python -m pytest tests/test_support_walkthrough.py -q

The test uses the two loopback ports. To exercise the Nexo pipeline separately, copy the project into an isolated working directory, then run:

mkdir -p /tmp/nexo-support-check
cp docs/walkthrough/support/*.nexo docs/walkthrough/support/nexo.toml /tmp/nexo-support-check/
cd /tmp/nexo-support-check
export SUPPORT_JWT_KEY=local-test-only
export SUPPORT_MODEL_KEY=local-fixture-only
python -m nexo ci run verify pipeline.nexo
python -m nexo ci export github verify pipeline.nexo

These fixed values are disposable test inputs, not deployment secrets. Backend tests fake the agent response and make no model call. The pipeline checks browser syntax and runs backend tests; its shell permission is for trusted CI execution and is incompatible with Shield’s foreign-code restrictions. Exporting writes CI configuration locally; review it and configure installation, working directory and credentials before enabling it in a repository.

5. Move beyond the local demo

  • Replace automatic demo sessions with authenticated users, per-user authorization and tenant-specific queries. Configure secure cookies and rotation.
  • Replace the model fixture and its synthetic usage with a supported provider, current model identifier and server-managed credentials. Update the network policy and assess data privacy, input limits and reported usage behavior.
  • Replace the development gateway with a validated same-origin hosting and session integration. Serve HTTPS, preserve Origin/CSRF validation and protect the backend listener.
  • Plan database migrations, backups, concurrency, rate limits and recovery. Test them on the actual host.
  • Build and review frontend releases with the Web deployment guide, and plan infrastructure with Nexo DevOps. Static frontend hosting alone cannot serve this application’s sessions or API.

The local integration is tested. Real model quality, paid-provider accounting, browser interaction, cloud deployment, production authentication, TLS, load behavior and full-app Shield isolation are not established by this walkthrough.
