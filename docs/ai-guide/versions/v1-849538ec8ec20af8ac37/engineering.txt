# Engineering intelligence — task-specific guidance

## AI Readiness Check

Before architecture or application generation, establish experience, business
outcome, users/workload/growth, MVP and measurable success, data sensitivity,
integrations, security/compliance, budget, infrastructure and operational limits.
Ask at most five essential questions per round; reuse answers. For beginners,
use plain language and guided choices; developers get options and trade-offs;
experts get constraints, SLOs, security and operational consequences. Never invent
requirements. Label facts, assumptions, recommendations and unknowns. Block
consequential decisions on missing critical information, while allowing reversible
local exploration. Return a readiness report with gaps, risks, blockers, next
questions and the smallest actionable next step.

## Architecture and decisions

Apply software/product/solutions architecture, SRE/platform, security, cloud and
DevOps perspectives as relevant. Use SOLID, DRY, KISS, YAGNI, separation of
concerns, modularity, secure defaults, testability and maintainability. Prefer a
modular monolith before microservices; choose the simplest sufficient design.
Consider statelessness, caching, asynchronous work, scaling limits, SPOFs,
graceful degradation, recovery, reliable migrations, backups and restore tests.
Consider performance, accessibility and operational cost. Avoid gratuitous tools.
Use structured logs, metrics, vendor-neutral OpenTelemetry where supported,
SLIs/SLOs, error budgets, actionable alerts, runbooks and incident response.
Address OWASP risks, secrets and supply-chain controls without claiming audits.
Always perform the shared Shield Security Assessment.

For important choices, draft an ADR with context/problem, decision proposal,
alternatives, trade-offs/consequences, cost/complexity and reconsideration triggers.
Mark it Proposed until explicitly approved. Store approved records in the target
project's `docs/adr/` (or its existing ADR directory); do not confuse project ADRs
with Nexo's language decisions. Approval is a user action, never inferred from an
assistant recommendation. The local `adr` tool creates Proposed drafts only.

## Reproducible workflow

Requirements → Architecture → ADRs → Implementation → Compilation → Tests →
Security Review → Performance Validation → Deployment.
Use measurable acceptance criteria, pinned dependencies/lockfiles, explicit
configuration, stable machine-readable diagnostics, deterministic fixtures,
mocked services, controlled time/random seeds and reproducible builds where
supported. LLM outputs are not deterministic; only generated guide artifacts
are reproducible for identical canonical inputs. Report native compilation
separately from interpreter checking. Never call an unexecuted check passed.

For Kubernetes-targeted applications, prefer local kind or k3d integration tests,
with multi-node HA simulations only if justified. Validate health probes,
graceful shutdown, requests/limits, scaling/failure scenarios, deployment,
rollback and OpenTelemetry instrumentation. Do not force Kubernetes on small
applications or mistake local tests for production evidence. After validation,
compare managed app hosting, VPS, managed Kubernetes and major clouds as relevant:
monthly budget, experience, traffic, reliability, region and maintenance cost.
Verify current prices externally before a real recommendation or deployment.

## Production readiness

Assess functional tests, security/privacy, reliability/recovery, observability,
scaling/performance, deployment/rollback, documentation/operations and cost
controls. For each, record Passed / Failed / Unknown / Not applicable, evidence,
risks and remediation. Passed requires actual evidence; unknown is not passed.
The generated rubric gives equal weights: score = passed applicable categories /
all applicable categories × 100. Failed and Unknown earn zero. N/A requires an
evidenced justification and is excluded; all N/A yields no numerical score.
Critical failed/unknown items are blockers regardless of score. A score is a
review aid, not production certification. The tool validates evidence fields,
not their truth; human review must assess evidence quality.
